## 1. ที่มาและปัญหา

ตอนนี้ใช้ Google Sheet Tab "แจ้งงาน" เป็นที่แจ้ง bug และปัญหาโปรแกรมให้ฝั่งโปรแกรมเมอร์ ใช้อ้างอิงว่าแจ้งวันไหน เริ่มทำวันไหน เสร็จวันไหน ใครแจ้ง ใครอนุมัติ ใครทำ และแก้ไขอย่างไร

| ปัญหา | ผลกระทบ |
|---|---|
| เซลล์แจ้ง Support แล้ว Support มาลงในชีต ไม่มีขั้นตอนให้หัวหน้า Support รับรู้ | ไม่แน่ใจว่าหัวหน้า Support รู้เรื่องหรือไม่ |
| ทำเสร็จหรือไม่เสร็จ ไม่มีใครแจ้งกลับ | เซลล์ไม่รู้สถานะงาน ต้องถามเอง |
| เห็นได้เฉพาะคนที่มีสิทธิ์ในลิงก์ | คนที่เกี่ยวข้องบางคน (เช่น เซลล์) ตามงานไม่ได้ |
| ฝ่ายอื่นลงความเร่งด่วนเอง แต่โปรแกรมเมอร์ติดงานอื่นอยู่ | ไม่มีคนจัดคิวว่างานไหนทำก่อน และไม่มีวันที่คาดว่าจะเสร็จที่เชื่อถือได้ |
| ไม่รู้ว่า Support ทดสอบอะไรมาแล้ว | โปรแกรมเมอร์ต้องถามซ้ำ หรือรับงานที่แก้ได้ที่หน้างาน |
| ทุกช่องพิมพ์เอง | ข้อมูลไม่สม่ำเสมอ (ดูด้านล่าง) |

**ข้อมูลที่ไม่สม่ำเสมอที่พบในชีต** (เหตุผลที่ระบบต้องบันทึกวันที่เอง และใช้ dropdown)

- ชื่อระบบเดียวกันพิมพ์หลายแบบ เช่น "HIP TIME 4.0", "HIPTIME 4.0", "HIPTime 4.0"
- รูปแบบวันที่ปนกัน (`dd/mm/yyyy`, `dd-mm-yyyy`, `d/m/yyyy`) และปีพิมพ์ผิดเป็น `226` (Id 36–38)
- วันที่เริ่มแก้ไขมาก่อนวันที่แจ้ง (Id 3, 65, 66)
- ปิดงานแล้วแต่ไม่มีวันที่แก้ไขเสร็จ (Id 33, 44, 46, 48, 52, 59, 62)
- สถานะ "ปิดงาน" แต่ช่องเลขที่คำขอเขียนว่า "ยังไม่ได้แก้ไข" (Id 66, 70)
- เลขที่คำขอ QP พิมพ์เอง และขาดช่วง (QP-20260608-31, -32)

## 2. เป้าหมายและขอบเขต

### 2.1 เป้าหมาย

1. **หัวหน้าฝ่ายรู้ทุกงานที่คนในฝ่ายแจ้ง** เพราะต้องอนุมัติก่อน และ**หัวหน้า Support รู้ทุกงานในระบบ**
2. **หัวหน้าโปรแกรมเมอร์เป็นคนจัดคิว** ทุกงานมีคนทำและวันที่คาดว่าจะเสร็จ
3. **ทุกคนที่เกี่ยวข้องได้รับแจ้งเตือน** เมื่อสถานะเปลี่ยน รวมถึงเซลล์ที่เป็นผู้ร้องขอ
4. **แต่ละคนเห็นงานตามสิทธิ์** ไม่ต้องแชร์ลิงก์
5. **วันที่และประวัติบันทึกอัตโนมัติ** จากการเปลี่ยนสถานะ แก้ย้อนหลังไม่ได้ ลบงานไม่ได้
6. **Support ระบุสิ่งที่ทดสอบมาแล้ว** ก่อนส่งงานถึงโปรแกรมเมอร์

### 2.2 ขอบเขต

| รายการ | ขอบเขต |
|---|---|
| ประเภทงาน | 4 ประเภท: **Bug / ขอเพิ่มฟีเจอร์-รุ่นเครื่อง / ทดสอบ-R&D / งานบริการข้อมูล** (เช่น ลบข้อมูล ลบเครื่องออกจากระบบ) |
| ผู้ใช้ | ภายในบริษัทเท่านั้น ไม่เกิน 50 คน ไม่เปิดให้ลูกค้าหรือตัวแทนจำหน่ายใช้ |
| ทีมพัฒนา | 1 คน |
| เปิดใช้งาน | เว็บ (responsive) ภายใน 1 สัปดาห์ แอปมือถือในสัปดาห์ที่ 2–4 |

## 3. ผู้ใช้ บทบาท และการมองเห็น

| บทบาท | ใคร | ทำอะไรได้ | เห็นงานไหน |
|---|---|---|---|
| **คนแจ้งงาน** | ทุกคนที่มีบัญชี (Support, Sale, Product, อื่นๆ) ส่วนใหญ่เป็น Support | สร้างงาน, แก้ไขจนกว่าจะอนุมัติ, ยกเลิกก่อนเริ่มแก้ไข, คอมเมนต์, เพิ่มผู้ติดตาม, ปิดงาน / ส่งงานกลับให้โปรแกรมเมอร์ | งานที่ตัวเองแจ้ง เป็นผู้ร้องขอ หรือเป็นผู้ติดตาม |
| **ผู้ร้องขอ / ผู้ติดตาม** | ผู้ใช้ที่ถูกใส่ชื่อในงาน | คอมเมนต์ ได้รับแจ้งเตือน เปลี่ยนสถานะไม่ได้ | งานที่ถูกใส่ชื่อ |
| **หัวหน้าฝ่าย** | ฝ่ายละ 1 คน | อนุมัติ / ตีกลับงานที่คนในฝ่ายแจ้ง (แก้ข้อมูลงานไม่ได้), ปิดงาน / ส่งกลับแทนคนแจ้ง, เพิ่มผู้ติดตาม | เพิ่มงานที่คนในฝ่ายแจ้ง (ไม่รวมงานที่คนในฝ่ายเป็นแค่ผู้ร้องขอ) |
| **หัวหน้า Support** | หัวหน้าฝ่าย Customer Support | เหมือนหัวหน้าฝ่าย | **ทุกงาน** และได้รับแจ้งเตือนทุกการเปลี่ยนสถานะของทุกงาน |
| **โปรแกรมเมอร์** | คนในฝ่าย Software | เริ่ม / พัก / ขอข้อมูลเพิ่ม / จบงาน ของงานตัวเอง, เลื่อนวันที่คาดว่าจะเสร็จ | ทุกงาน (ใช้ค้นวิธีแก้ปัญหาเก่า) |
| **หัวหน้าโปรแกรมเมอร์** | 1 คน = หัวหน้าฝ่าย Software | จัดคิวทุกงาน, ไม่รับงาน (ไม่ดำเนินการ), ย้ายคนทำ, เรียงคิว, เลื่อนวัน, แก้ข้อมูลจำแนกตอนจัดคิว, เพิ่มผู้ติดตาม, รับงานไปทำเองได้ | ทุกงาน |
| **Admin** | ผู้พัฒนาระบบ | จัดการผู้ใช้ ฝ่าย ข้อมูลหลัก และการตั้งค่า, ตั้งรหัสผ่านใหม่, ปิดบัญชี — **อนุมัติหรือจัดคิวแทนไม่ได้** | ทุกงาน |

**กฎ**

- ผู้อนุมัติคือ**หัวหน้าฝ่ายของคนแจ้ง** ฝ่ายละ 1 คนเท่านั้น ถ้าหัวหน้าฝ่ายลา งานรอจนหัวหน้ากลับมา (อนุมัติผ่านเว็บในมือถือได้)
- ถ้าคนแจ้งเป็นหัวหน้าฝ่ายเอง ระบบอนุมัติให้อัตโนมัติ (ข้ามไป "รอจัดคิว")
- หัวหน้าฝ่าย Software คือหัวหน้าโปรแกรมเมอร์ งานที่คนในฝ่าย Software แจ้ง หัวหน้าโปรแกรมเมอร์อนุมัติแล้วจัดคิวต่อได้ทันที
- หัวหน้าโปรแกรมเมอร์จัดคิวได้คนเดียว ถ้าลา งานรอใน "รอจัดคิว"
- ฝ่ายเริ่มต้น 4 ฝ่าย: **Customer Support, Sale, Product & Innovation, Software** และ Admin เพิ่มฝ่ายได้ ทุกฝ่ายต้องมีหัวหน้า (หน้า Admin เตือนถ้าฝ่ายไหนยังไม่มี)

## 4. ขั้นตอนของงาน (สถานะ)

### 4.1 ภาพรวม

```text
 สร้างงาน
    │  (คนแจ้งเป็นหัวหน้าฝ่าย → ข้ามไป "รอจัดคิว")
    ▼
 รออนุมัติ ──ตีกลับ──► ตีกลับ ──แก้แล้วส่งใหม่──► รออนุมัติ
    │ อนุมัติ (หัวหน้าฝ่ายของคนแจ้ง)
    ▼
 รอจัดคิว ──────────────────────► ไม่ดำเนินการ (หัวหน้าโปรแกรมเมอร์ ใส่เหตุผล)
    │ จัดคิว (หัวหน้าโปรแกรมเมอร์)
    ▼
 อยู่ในคิว ◄──── พักงาน ────┐
    │ เริ่มแก้ไข             │
    ▼                       │
 กำลังแก้ไข ────────────────┘
    │ จบงาน (คนทำ กรอก "การแก้ไข")
    ▼
 จบงาน (รอปิด) ──ส่งกลับ (ใส่เหตุผล)──► กำลังแก้ไข
    │ คนแจ้งปิด หรือระบบปิดเองเมื่อครบ 3 วันทำการ
    ▼
 ปิดงาน

 รอข้อมูลเพิ่ม : เข้าจาก "รอจัดคิว" (หัวหน้าโปรแกรมเมอร์) หรือ "กำลังแก้ไข" (คนทำ)
                 พอคนแจ้งคอมเมนต์ตอบ งานกลับไปขั้นเดิมเอง
 ยกเลิก       : คนแจ้งยกเลิกได้ (ใส่เหตุผล) ถ้างานยังไม่เคยเข้า "กำลังแก้ไข"
 ไม่ดำเนินการ  : หัวหน้าโปรแกรมเมอร์ปิดได้ทุกขั้น ตั้งแต่ "รอจัดคิว" จนถึงก่อน "จบงาน"
```

| จบงาน → ปิดงาน (อัตโนมัติ) | ระบบ | — | ครบ 3 วันทำการ (เตือนคนแจ้งก่อน 1 วัน) |

| รออนุมัติ / ตีกลับ / รอจัดคิว / อยู่ในคิว / รอข้อมูลเพิ่ม → ยกเลิก | คนแจ้ง (เฉพาะงานที่ยังไม่เคยเข้า "กำลังแก้ไข") | เหตุผล | |
| รอจัดคิว / อยู่ในคิว / กำลังแก้ไข / รอข้อมูลเพิ่ม → ไม่ดำเนินการ | หัวหน้าโปรแกรมเมอร์ | เหตุผล | ใช้ทำรายงาน |

นอกจากเปลี่ยนสถานะ ยังมีการเปลี่ยนแปลงอื่นอีก 3 แบบ
- **เลื่อนวัน:** หัวหน้าโปรแกรมเมอร์หรือคนทำเลื่อนได้ ต้องใส่เหตุผล
- **ย้ายคนทำ:** หัวหน้าโปรแกรมเมอร์เท่านั้น
- **แก้ข้อมูลจำแนก:** หัวหน้าโปรแกรมเมอร์แก้ได้ตอนจัดคิว

**ทุกการเปลี่ยนแปลงลง Timeline** ว่าใครทำ เปลี่ยนจากอะไรเป็นอะไร เมื่อไร และหมายเหตุ รวมถึงการแก้ข้อมูลงาน

## 5. การจัดคิวและ Kanban

### 5.1 การจัดคิว

- **ทุกงานต้องผ่านการจัดคิว** แม้คนแจ้งเลือก "ทำทันที" ไม่มีทางลัด
- งานที่คนแจ้งเลือก "ทำทันที" แสดงบนสุดในหน้ารอจัดคิว และแจ้งเตือนหัวหน้าโปรแกรมเมอร์ทันทีที่อนุมัติ
- หัวหน้าโปรแกรมเมอร์เลือกได้ 3 แบบ: **รับเข้าคิว / ขอข้อมูลเพิ่ม / ไม่ดำเนินการ**
- รับเข้าคิวต้องกำหนด
  - **ความเร่งด่วนจริง** (ทำทันที / ด่วน / ปกติ) — หน้างานแสดงคู่กับ "ความเร่งด่วนที่ขอ"
  - **คนทำ** — ระบบใส่ผู้รับผิดชอบหลักของระบบ/โปรแกรมนั้นไว้ให้ก่อน เปลี่ยนได้
  - **วันวางแผนเริ่ม และวันคาดว่าจะเสร็จ** — วันคาดว่าจะเสร็จใช้เป็น Deadline (ไม่มีการคำนวณ Deadline อัตโนมัติจากความเร่งด่วน)
- ตอนจัดคิว หัวหน้าโปรแกรมเมอร์**แก้ระบบ/โปรแกรม ประเภทงาน รุ่นเครื่อง และลูกค้าได้** เช่น คนแจ้งเลือกระบบผิด (บันทึกลง Timeline)

### 5.2 การเลื่อนวัน

- หัวหน้าโปรแกรมเมอร์ หรือคนทำ เลื่อนวันวางแผนเริ่ม / วันคาดว่าจะเสร็จได้
- ต้องใส่เหตุผลทุกครั้ง ระบบเก็บประวัติ (วันเดิม → วันใหม่, ใคร, เหตุผล) และนับจำนวนครั้งที่เลื่อน
- แจ้งเตือนคนแจ้ง ผู้ร้องขอ และผู้ติดตาม ถ้าคนทำเป็นคนเลื่อน แจ้งหัวหน้าโปรแกรมเมอร์ด้วย

### 5.3 Kanban (สัปดาห์แรก)

- **คอลัมน์ = สถานะ:** รอจัดคิว | อยู่ในคิว | กำลังแก้ไข | รอข้อมูลเพิ่ม | จบงาน (รอปิด)
- **แถว (swimlane) = โปรแกรมเมอร์** รวมหัวหน้าโปรแกรมเมอร์ และมีแถว "ยังไม่จัดคิว" สำหรับงานที่ยังไม่มีคนทำ
- การ์ดแสดงเลขที่งาน หัวข้อ ระบบ ความเร่งด่วนจริง (และที่ขอ) วันคาดว่าจะเสร็จ และป้าย "เลยกำหนด"

| การลาก | ใครทำได้ | ผล |
|---|---|---|
| ขึ้นลงในคอลัมน์ "อยู่ในคิว" | หัวหน้าโปรแกรมเมอร์ | เรียงลำดับคิวของคนทำ |
| ไปแถวของคนอื่น | หัวหน้าโปรแกรมเมอร์ | เปลี่ยนคนทำ (แจ้งเตือนทั้งคนเดิมและคนใหม่) |
| จาก "รอจัดคิว" ไป "อยู่ในคิว" | หัวหน้าโปรแกรมเมอร์ | เปิดฟอร์มจัดคิว |
| ข้ามคอลัมน์อื่นๆ | คนทำ (เฉพาะการ์ดตัวเอง) และหัวหน้าโปรแกรมเมอร์ | เปลี่ยนสถานะตามข้อ 4.3 ถ้าต้องกรอกข้อมูล (เช่น ไป "จบงาน" ต้องกรอก "การแก้ไข") ระบบเปิดหน้าต่างให้กรอกก่อน |

ในแอปมือถือ Kanban เป็นรายการแยกตามสถานะที่เลื่อนดูได้ ไม่มีการลาก (ลากเรียงทำบนเว็บ)

## 8. Login บัญชีผู้ใช้ และภาษา

| ช่วง | วิธี Login |

## 11. Server การเข้าถึง และการสำรองข้อมูล

| รายการ | รายละเอียด |
|---|---|
| Server | Windows Server + IIS + SQL Server ที่บริษัทใช้รันระบบอื่นอยู่แล้ว (HR Platform ยังไม่ขึ้น Server จึงยังใช้ร่วมไม่ได้) |
| สัปดาห์แรก | เข้าผ่าน **IP เฉพาะในเครือข่ายบริษัท** (และ VPN ถ้ามี) — ไม่เปิดออกอินเทอร์เน็ต เพราะยังไม่มี HTTPS รหัสผ่านจะถูกส่งแบบไม่เข้ารหัส |
| ก่อนปล่อยแอป | ทำ **subdomain + HTTPS** (เช่น `swcare.hipglobal.co.th`) แล้วจึงเปิดให้เข้าจากนอกบริษัท — iOS และ Android บล็อก HTTP ธรรมดาเป็นค่าเริ่มต้น |
| สำรองข้อมูล | ฐานข้อมูลและโฟลเดอร์ไฟล์แนบ ทุกคืน เก็บย้อนหลัง 30 วัน และ copy ไปอีกเครื่องหรือ NAS ถ้ามี |
| ภายหลัง | ย้ายไป Cloud พร้อม HR Platform |

## 12. นำเข้าข้อมูลเดิมจาก Google Sheet

- Export Tab "แจ้งงาน" เป็น CSV แล้วใช้ตัวนำเข้าที่เขียนไว้ใช้ครั้งเดียว

- ชื่อคนในชีตจับคู่กับบัญชีผู้ใช้ ชื่อที่จับคู่ไม่ได้ (เช่น "KUNG HIP", "callcenter HIP") เก็บเป็นข้อความ
- เก็บเลข QP/RQ เดิมไว้ในช่อง "เลขอ้างอิงเดิม"
- งานที่นำเข้าไม่ต้องมี "สิ่งที่ทดสอบแล้ว"

| ข้อมูลในชีต | นำเข้าเป็น |
|---|---|
| 63 งานที่ "ปิดงาน" | ปิดงาน ใช้วันที่ตามชีต งานที่วันที่ผิดปกติหรือข้อมูลขัดกัน (ปี `226`, วันเริ่มก่อนวันแจ้ง, Id 66 และ 70 ที่เขียน "ยังไม่ได้แก้ไข") ติดธง "ข้อมูลเดิมต้องตรวจ" |
| Id 65, 69 ("แจ้งงาน" แต่มีวันเริ่มแก้ไขแล้ว) | กำลังแก้ไข ให้ผู้รับผิดชอบหลักของระบบนั้น |
| Id 25, 51, 56, 60, 68 ("แจ้งงาน") | รอจัดคิว ให้หัวหน้าโปรแกรมเมอร์จัดคิว ไม่ต้องผ่านขั้นอนุมัติอีก เพราะในชีตอนุมัติแล้ว |
| Id 34 (แถวว่าง) | ไม่นำเข้า |

ถ้าสัปดาห์แรกไม่ทัน การนำเข้าเป็นงานแรกที่เลื่อนไปสัปดาห์ที่ 2 ระหว่างนั้นยังเปิดดูชีตเดิมได้ (อ่านอย่างเดียว)

## 13. แผนเวลา

### 13.1 สัปดาห์ที่ 1 — เปิดใช้เว็บ

| วัน | งาน |
|---|---|

### 13.2 ถ้าไม่ทัน เลื่อนตามลำดับนี้

3. ผู้ติดตาม

ขั้นตอนงานหลัก, Kanban + ลากเรียง และไฟล์แนบ ต้องเสร็จในสัปดาห์แรกไม่ว่ากรณีใด
